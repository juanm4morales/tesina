\chapter{Arquitectura de Software y Patrones de Diseño}
\label{apendice:arquitectura_software}

En este apéndice se detalla la arquitectura de software del marco computacional \texttt{marlTLC}, sus especificaciones de diseño orientado a objetos, los diagramas de clases UML y la justificación de los patrones de diseño adoptados para desacoplar los componentes de simulación, aprendizaje por refuerzo y cálculo de recompensas.

\section{Diseño Orientado a Objetos del Entorno de Simulación}
\label{sec:apendice_uml_entorno}

La infraestructura de simulación se estructura siguiendo una separación estricta de responsabilidades. La clase abstracta \texttt{BaseSumoEnvironment} encapsula la inicialización de SUMO, el control temporal y la interacción de bajo nivel con la API \texttt{libsumo} / \texttt{traci}. A partir de ella, \texttt{SumoRllibEnv} adapta la simulación a la interfaz estándar \texttt{MultiAgentEnv} de Ray RLlib.

\section{Jerarquía de Funciones de Recompensa y Patrón Strategy}
\label{sec:apendice_uml_recompensas}

El cálculo de la recompensa se desacopla mediante el patrón \textbf{Strategy}, permitiendo intercambiar de forma transparente la métrica de optimización sin alterar el bucle principal de simulación.

La clase base abstracta \texttt{RewardFn} define la interfaz común \texttt{compute\_reward(tl\_id)}. Las clases concretas implementan formulaciones locales basadas en demoras acumuladas (\texttt{DiffAccWaitingTimeReward}), longitud de colas (\texttt{NegativeQueueLengthReward}) o presión de red (\texttt{PressureReward}). La coordinación distribuida se logra mediante el patrón \textbf{Composite}, implementado en \texttt{NeighborhoodRelevanceReward}, el cual combina de manera convexa la señal local y la señal promedio de los semáforos adyacentes provista por \texttt{NeighborAvgReward}.

\section{Patrones de Diseño Implementados}
\label{sec:apendice_patrones_diseno}

A lo largo del marco computacional \texttt{marlTLC} se aplican los siguientes patrones de diseño de software reconocidos:

\begin{enumerate}
    \item \textbf{Patrón Strategy (Estrategia):}
    \begin{itemize}
        \item \textit{Propósito:} Encapsular algoritmos de cálculo de recompensa y permitir su variación independiente de los controladores semafóricos.
        \item \textit{Implementación:} Interfaz base \texttt{RewardFn} y clases derivadas (\texttt{DiffHaltedReward}, \texttt{DiffAccumulatedWaitingTimeReward}, \texttt{PressureReward}, \texttt{SpillbackPenaltyReward}).
    \end{itemize}

    \item \textbf{Patrón Factory Method y Registry (Fábrica con Registro Dinámico):}
    \begin{itemize}
        \item \textit{Propósito:} Instanciar dinámicamente funciones de recompensa y módulos neuronales a partir de cadenas de configuración o especificaciones compuestas (\texttt{RewardSpec}), permitiendo registrar nuevas funciones sin modificar la fábrica (Principio Abierto/Cerrado).
        \item \textit{Implementación:} Clase \texttt{RewardFactory} y decorador \texttt{@register\_reward(name)}.
    \end{itemize}

    \item \textbf{Patrón Composite (Objeto Compuesto):}
    \begin{itemize}
        \item \textit{Propósito:} Construir recompensas cooperativas y multifactoriales tratando componentes individuales y combinaciones de manera uniforme.
        \item \textit{Implementación:} \texttt{WeightedCompositeReward} y \texttt{NeighborhoodRelevanceReward}, que agregan recompensas locales y vecinales mediante combinaciones lineales o convexas.
    \end{itemize}

    \item \textbf{Patrón Protocol / Structural Subtyping (Tipado Estructural):}
    \begin{itemize}
        \item \textit{Propósito:} Desacoplar el proveedor de métricas vecinales del tipo concreto \texttt{TrafficLight}, facilitando la prueba unitaria con objetos simulados (\textit{mocks}) y evitando dependencias circulares.
        \item \textit{Implementación:} Protocolo \texttt{NeighborInfoProvider} (\texttt{src/marlTLC/environments/protocols.py}) con el decorador \texttt{@runtime\_checkable}.
    \end{itemize}

    \item \textbf{Patrón Adapter (Adaptador):}
    \begin{itemize}
        \item \textit{Propósito:} Traducir la API procedural y basada en comandos de TraCI / \texttt{libsumo} a las interfaces orientadas a objetos y vectorizadas de \texttt{MultiAgentEnv} (Ray RLlib) y \texttt{ParallelEnv} (PettingZoo).
        \item \textit{Implementación:} \texttt{SumoRllibEnv} y \texttt{Observation}.
    \end{itemize}

    \item \textbf{Patrón Decorator (Decorador):}
    \begin{itemize}
        \item \textit{Propósito:} Extender dinámicamente las capacidades de los módulos sin alterar su jerarquía de herencia.
        \item \textit{Implementación:} Decoradores de registro \texttt{@register\_reward} y envoltura de módulos de acción en PyTorch (\texttt{ActionMaskingTorchRLModule}).
    \end{itemize}
\end{enumerate}
